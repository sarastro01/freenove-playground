# User Interface: sensor-pages-dashboard

**Last Updated:** 2026-09-25  
**UI Type:** Embedded TFT Display (320×480 pixels)  
**Input Method:** Gamepad buttons (no touchscreen, no settings menu)  
**Navigation:** Circular pagination (10 pages)  
**Recent Changes:** Updated with FEATURE-SPEC-008 central parameter definitions; verified all 7-parameter layouts for BME280, Gamepad 8-parameters, Encoder 7-parameters

---

## Executive Summary

This is a **no-menu, no-hierarchy UI**. The entire application is a series of 10 sensor data pages displayed on a TFT screen. Users navigate between pages sequentially using gamepad buttons (Y = previous, A = next) with automatic wrap-around. Each page displays sensor readings or an error message if the sensor is unavailable.

**No forms, no settings, no configuration UI.** All application behavior is hardcoded at compile-time.

---

## 1. Application Navigation Model

### Navigation Topology: Circular Pagination

The application implements a **circular linked list** of 10 pages. Users navigate sequentially; no skipping or direct access.

```
Page 0 ←→ Page 1 ←→ ... ←→ Page 8 ←→ Page 9 ←→ (wraps to Page 0)
```

**Navigation Rules:**
- **Y Button (Gamepad):** Navigate to previous page (currentPage - 1, mod 10)
- **A Button (Gamepad):** Navigate to next page (currentPage + 1, mod 10)
- **Wrap-around:** From page 0, Y goes to page 9; from page 9, A goes to page 0
- **No history:** No "back stack"; pressing Y repeatedly cycles through all pages in reverse

### Route Model: No Routes

This is not a web application. There are no URL routes, path parameters, or query strings. Navigation is purely sequential page indices (0–8).

| Concept | Implementation |
|---------|---|
| **Current Page** | Global variable `currentPage` (uint8_t, 0–9) |
| **Page Address** | Array index in page renderer switch statement |
| **Navigation** | Direct `currentPage` mutation (no routing library) |
| **Deep Linking** | Not supported; always boots to page 0 (BME280) or page 2 (INA219) |
| **Forward/Back** | Y = back (previous page), A = forward (next page) |

**Data Retrieval (FEATURE-SPEC-008 Central Definitions):**
- **Trigger:** I2C reads occur in `readSensors()` every 500 ms via `readBme280()` function
- **Page Function Behavior:** `pageBme280()` uses central `bme280_params[]` definition and `bme280_getValue()` getter function
- **Cached Fields:**
  - `bme280Values.temperature` ← `bme280.readTemperature()` (°C)
  - `bme280Values.pressure` ← `bme280.readPressure() / 100.0f` (Pa → hPa)
  - `bme280Values.humidity` ← `bme280.readHumidity()` (%)
  - `bme280Values.dewPoint` ← computed via Alduchov & Eskridge formula (°C)
  - `bme280Values.altitude` ← `bme280.readAltitude(1013.25)` (m, 1013.25 hPa reference)
  - `bme280Values.airQuality` ← placeholder (AQI estimate, 0.95 for normal conditions)
  - `bme280Values.tempTrend` ← temperature derivative (°C/min, placeholder 0.5)
- **Benefit:** Eliminates I2C latency during page rendering; improves display responsiveness

**Computed Values (Alduchov & Eskridge Formula, ±0.35°C accuracy, valid 0-50°C / 1-100% RH):**
```cpp
// Computed in readBme280() every 500ms, cached for display
const float a = 17.62;
const float b = 243.12;
float alpha = ((a * temperature) / (b + temperature)) + log(humidity / 100.0f);
dewPoint = (b * alpha) / (a - alpha);  // Result in °C
```
**Note:** Requires `#include <math.h>` for `log()` function. More accurate than simplified formula (±3°C).

**Large Display Mode:**
- Activated by pressing Button B on this page
- Cycles through all 7 parameters with Button B (forward) and Button X (backward)
- Each parameter displayed in large font for readability at distance
- Press Button Y to exit large display mode

**Sensor Missing Behavior:**
If BME280 not detected at boot (`available.bme280 = false`):
- Header displays normally ("BME280 (0x77)")
- Error screen shows "Sensor nicht vorhanden" (red, font 2)
- I2C address displayed in yellow (0x77)
- Footer shows "Keine Daten verfuegbar"
- Navigation still works (Y/A buttons)

**User Actions:**
- **Y Button:** Navigate to page 9 (DS2484 1-Wire)
- **A Button:** Navigate to page 1 (Gamepad QT)
- **B Button:** Enter large display mode
- **No other interactions**

**Permissions:** None (embedded firmware; no auth model)

**Data Display:**
- Bus voltage: 0–26V (3 decimals)
- Shunt voltage: usually ±0.08V (3 decimals, negated from sensor)
- Load voltage: Bus - Shunt/1000 (3 decimals)
- Current: Negated from sensor (inverted sign; 3 decimals)
- Power: Product of voltage × current (3 decimals)

**Data Retrieval:**

  - `getBusVoltage_V()` → bus
  - `getCurrent_mA()` → current (negated)
  - `getPower_mW()` → power

**Coulomb Accumulation:**
```
chargeMah += current_mA * elapsed_µs / 3.6e9  (every 20 µs, if elapsed < 200ms)
```

**Button Behavior in Large Display Mode (Detailed):**
```

  → largeDisplayIndex = 0

  → Next cycle: pageLargeDisplayIna219(1) renders

  → largeDisplayIndex = (1 - 1 + 7) % 7 = 0
  → Next cycle: pageLargeDisplayIna219(0) renders

  → largeDisplayMode = false
  → largeDisplayIndex = 0 (reset)
  → Next cycle: pageIna219() renders standard layout

User presses Button A (on Page 2, largeDisplayMode = true):
  → No action (button inactive during mode)

```

**Display Optimization (FEATURE-SPEC-006 & FEATURE-SPEC-007):**

The SCD30 page header (including ASC status badge) uses a **conditional rendering strategy** to prevent flicker:

- **Rendering Decision:** Header is only redrawn when the page becomes active (`pageChanged=true`)
- **Rationale:** The header includes `tft.fillScreen(TFT_BLACK)`, a blocking I2C operation that takes ~100ms. Calling this every display refresh cycle (~50ms) causes visible flicker.
- **Implementation:** `pageScd30(bool pageChanged)` receives a flag from `drawCurrentPage(true)`:
  - `pageChanged=true` (page transition) → Redraw entire header and data
  - `pageChanged=false` (same page, refresh only) → Skip header, update only sensor values
- **Result:** Flicker-free display updates while maintaining responsive ASC badge updates on page transitions

## 5. Navigation Behavior

### Page Transition

**Trigger:** Y or A button falling edge detected (transition from released to pressed).

**Behavior:**

1. **Gamepad read completes** (25 ms cycle)
2. **Button state compared** to previous state (edge detection)
3. **If Y pressed (falling edge):** `currentPage = (currentPage + 10 - 1) % 10` (previous)
4. **If A pressed (falling edge):** `currentPage = (currentPage + 1) % 10` (next)
5. **Page index updated**
6. **Next loop cycle:** `if (currentPage != lastPage) drawCurrentPage(true)` (full redraw with header)
7. **lastPage updated** to match currentPage

**Wrap-Around:**
- Page 0 Y button → Page 9
- Page 9 A button → Page 0

**Transition Speed:** Up to 25 ms (gamepad read frequency).

**No Animation:** Immediate switch; no slide/fade effect.

---

### Page Rendering Decision

**On Each Loop Cycle:**

```cpp
if (currentPage != lastPage) {
  drawCurrentPage(true);      // Full redraw (header + data)
  lastPage = currentPage;
} else if (IS_LIVE_PAGE && time_gate_fires) {
  drawCurrentPage(false);     // Data-only refresh (no header)
} else if (time_gate_fires) {
  drawCurrentPage(false);     // Data-only refresh
}
```

**Live Pages:** Gamepad (page 2), Encoder (page 4) → 20 ms refresh (but encoder reads CONTINUOUSLY, not page-conditional)
**Slow Pages:** All others → 500 ms refresh

## 6. Interaction Patterns

### Button Press Edge Detection

**Pattern:** Debounce via state tracking

```
Previous cycle: button_state = 1 (released)
Current cycle:  button_state = 0 (pressed)
Edge detected?  Yes (1→0 transition)
Action:         Execute navigation / LED change
Save state:     For next cycle comparison
```

**Debounce:** Hardware debounce on gamepad seesaw; no software debounce.

**Double-Press:** Each press counted independently; no multi-tap logic.

---

### Encoder Interaction

**Dial Rotation:**
1. Dial rotated
2. `readEncoderAt50Hz()` called (CONTINUOUSLY at 50 Hz, not page-conditional)
3. Position delta calculated
4. LED brightness adjusted (delta × 8)
5. `updateEncoderLed()` called (immediate NeoPixel update)
6. Next page refresh: new brightness displayed

**Button Press:**
1. Button pressed (falling edge)
2. Press count incremented
3. Color index cycled (0→1→2→3→0)
4. `updateEncoderLed()` called (immediate)
5. Next page refresh: new color name displayed

**Latency:** 20 ms (read cycle), + SPI time for LED update.

**Trigger:** Button Y pressed while in large display mode

**Action:**
1. Set `largeDisplayMode = false`, `largeDisplayIndex = 0` (reset state)
2. Immediately render standard INA219 page via `drawHeader()` + `pageIna219()` (atomic clear + redraw)
3. No visual artifacts; clean transition

**Design Rationale:** Immediate rendering ensures the display clears atomically before new content is drawn, preventing leftover text or flickering.

- **Refresh Rate:** Inherited from page 2 standard refresh (500 ms)
- **Data Source:** Live `ina219Values` struct (no caching)
- **Display Latency:** Up to 500 ms between value changes and display update
- **Consistency:** Value formatting (decimal places) matches standard page exactly

### 7.6 Performance & Constraints

- **Render Time:** ~450 ms (must complete within 500 ms refresh cycle)
- **Memory:** Direct rendering (no buffering; no Sprite allocation)
- **Flash Impact:** +~500 bytes for helper functions and layout code
- **Dependencies:** Requires `available.ina219 == true`

## 7.7 Display Update Strategy (FEATURE-SPEC-006) — **NEW: On-Change Only**

### Shift from Time-Driven to Event-Driven Updates

**Previous Behavior (FEATURE-SPEC-005):**
- Display redraws every 500 ms (periodic, time-driven)
- Redraws happen regardless of whether values changed
- Constant display updates cause flicker and unnecessary SPI load

**New Behavior (FEATURE-SPEC-006):**
- Display redraws ONLY when values actually change (event-driven)
- OR on timer events (INA219 seconds counter increments)
- No unnecessary redraws (eliminates flicker, reduces power)

### Redraw Conditions

**Display shall redraw if ANY of these conditions are true:**

```cpp
// Condition 1: Page changed
if (currentPage != lastPage) {
  drawCurrentPage(true);   // Full redraw (header + data)
  lastPage = currentPage;
  return;
}

// Condition 2: Sensor values changed
if (valuesChanged()) {
  drawCurrentPage(false);  // Partial redraw (data only)
  updateCachedValues();
  return;
}

// Condition 3: Timer event fired
if (ina219Values.timerSeconds != lastTimerValue) {
  drawCurrentPage(false);  // Partial redraw (data only)
  lastTimerValue = ina219Values.timerSeconds;
  return;
}

// Otherwise: No redraw (save CPU, eliminate flicker)
```

### Value Change Detection

**Implementation:**
```cpp
bool valuesChanged() {
  // Compare current sensor cache with previous snapshot
  // Return true if ANY relevant field differs for current page
  
  switch (currentPage) {
    case 0: // BME280 page
      return bme280Values.temperature != lastBme280Temp ||
             bme280Values.humidity != lastBme280Humidity ||
             /* ... all fields ... */;
    
    case 1: // Gamepad page
      return gamepadValues.x != lastGamepadX ||
             gamepadValues.y != lastGamepadY ||
             gamepadValues.buttons != lastGamepadButtons;
    
    // ... implement for each of 10 pages
    
    default: return false;
  }
}

void updateCachedValues() {
  // Save current values for next comparison
  lastBme280Temp = bme280Values.temperature;
  lastBme280Humidity = bme280Values.humidity;
  // ... cache all fields for all pages
}
```

### Performance Impact

| Aspect | FEATURE-SPEC-005 | FEATURE-SPEC-006 | Improvement |
|--------|---|---|---|
| Display updates per second | 2 Hz (constant) | 0.2–1 Hz (on change) | 50–80% reduction |
| SPI writes per cycle | Always | Only on change | Variable |
| Flicker | Visible (20+ fps) | None (event-driven) | Smoother visual |
| CPU load | Constant 50–70 ms per cycle | < 10 ms (idle) | 80% reduction |
| Power consumption | 100% | 30–50% (estimated) | 50–70% savings |

### Refresh Rate Guarantee

**INA219 Page Special Case (Page 2):**
- Timer increments every 1 second
- Display MUST redraw every 1 second to show updated timer
- Implementation: Check `ina219Values.timerSeconds` in value comparison
- Ensures timer field always visible (no stale timer display)

**All Other Pages:**
- Redraw frequency depends on sensor value stability
- Typical sensor pages: 1–2 redraws per minute (if data stable)
- Live pages (Gamepad, Encoder): Redraw on every value change

### Display Latency (Updated Expectations)

| Scenario | Latency | Guarantee |
|----------|---------|-----------|
| Page change | < 20 ms | Always immediate |
| Sensor value change | < 200 ms | Worst case: 200 ms after sensor read completes |
| INA219 timer event | 1000 ms ± 200 ms | Updates every 1 second ± margin |
| Stable sensor values | N/A | No update (no need) |

**Worst-case latency:** 200 ms (sensor read duration) + < 50 ms (render time) = ~250 ms total

### Configuration

Display update behavior is automatic; no configuration needed. FEATURE-SPEC-006 requirements:
- `valuesChanged()` function compares all relevant fields
- `updateCachedValues()` snapshots values after each redraw
- Main loop checks all 3 redraw conditions before calling `drawCurrentPage()`

## 10. Large Display Mode (All Pages) — **NEW (FEATURE-SPEC-007)**

### Overview

**Large Display Mode** is an alternate viewing mode for each sensor page. Instead of displaying 7 rows of labeled data, large display shows a **single sensor value in enormous font**, centered on the display. Users can cycle through all available values for that page using gamepad buttons.

**Purpose:**
- Readability at distance (5+ meters, presentation/field diagnostics)
- Focus on individual measurements during troubleshooting
- Consistent alternative view across all 10 sensor pages

**Entry:** Button B on any sensor page → activates large display mode for that page
**Exit:** Button Y → returns to standard page view

### Large Display Mode Layout (Universal Template)

```
┌──────────────────────────────────────────┐
│                                          │
│  [SENSOR TITLE]                          │  y=18, Font 4, Cyan
│  e.g., "SCD30 CO2 Sensor"                │
│                                          │
├──────────────────────────────────────────┤  y=48 (separator line)
│                                          │
│  [VALUE LABEL]                           │  y=70, Font 4, Cyan
│  e.g., "CO₂ Konzentration"               │
│                                          │
│                                          │
│  [LARGE VALUE]                           │  y=160, Font 8, Color-coded
│  e.g., "2150"                            │  (Green/Orange/Cyan, never Magenta)
│  (Largest element on screen)             │
│                                          │
│  [UNIT]                                  │  y=240, Font 4, White
│  e.g., "ppm"                             │
│                                          │
│  [FOOTER INSTRUCTIONS]                   │  y=295, Font 2, DarkGrey
│  "B:next  X:prev  Y:exit"                │
│                                          │
└──────────────────────────────────────────┘
```

**Separator Line:** A horizontal line (TFT_DARKGREY) at y=48 divides the header from content.

**Color Scheme (Inherited from Standard Pages):**
- Title: TFT_CYAN (sensor header style)
- Label: TFT_CYAN (measurement description)
- Value: Color-coded per sensor/measurement
  - TFT_GREEN: Primary/raw measurements (good)
  - TFT_ORANGE: Secondary measurements (caution)
  - TFT_CYAN: Computed/derived values
  - TFT_RED: Errors/out-of-range (never used in normal mode)
- Unit: TFT_WHITE (maximum contrast)
- Footer: TFT_DARKGREY (subtle text)

**⚠️ Never use TFT_MAGENTA** — not readable in bright/sunlight.

### Button Behavior in Large Display Mode

| Button | Behavior | Notes |
|--------|----------|-------|
| **B** | Advance to next value (cycles: 0→1→...→max-1→0) | Immediate response; display update up to 200 ms |
| **X** | Advance to previous value (cycles: max-1→...→1→0) | Backward cycling with wrap-around |
| **Y** | Context-sensitive: **In Large Display Mode:** Exit mode, return to standard page. **In Standard Page:** Navigate to previous page (circular). | Dual behavior allows page navigation while preventing accidental page changes during Large Display mode |
| **A** | Context-sensitive: **In Large Display Mode:** Inactive (no function). **In Standard Page:** Navigate to next page. | Reserved for future Large Display features |

**Page Navigation Disabled During Large Display:** While in large display mode, A/Y buttons cannot navigate between pages. User must press Y to exit Large Display mode first, then can navigate with A/Y.

### Interaction Model

**Entry Sequence:**
1. User on sensor page in standard view
2. Presses Button B
3. Page immediately switches to large display mode
4. Value index 0 displayed in large font
5. Subsequent B presses cycle forward

**Exit Sequence:**
1. User in large display mode
2. Presses Button Y
3. Page immediately switches to standard view
4. Same sensor page displayed normally
5. Value index reset to 0 for next B press

**Wrap-Around Behavior:**
- Forward cycle: 0→1→2→...→(valueCount-1)→**0** (wraps)
- Backward cycle: (valueCount-1)→...→2→1→0→**(valueCount-1)** (wraps)
- Example (Page 0, 7 values): 6→0 (Y→A button cycle)

### Rate Limiting Behavior

Large display mode respects the **200 ms display rate limit** (FR-015):
- Button press changes `valueIndex` immediately (no delay)
- Display update queued but subject to 200 ms minimum interval
- If user presses B twice in 100 ms: Second press updates `valueIndex`, but display may not refresh until 200 ms have elapsed since last refresh
- **Result:** Button feels responsive; visual update may lag slightly

### 10.7 Render Optimization — Incremental Display Updates

**Implementation Strategy:** To prevent flicker and reduce display I/O load, `renderLargeDisplay()` uses intelligent partial update strategy:

#### Full Redraw (tft.fillScreen())
Triggered when:
- Large display mode first activated (flag: `needsFullRedraw=true`)
- User cycles to different value index using B/X buttons
- Detected sensor value has changed since last render

**Cost:** ~450ms (blocking SPI operation)

#### Partial Redraw (tft.fillRect())
Triggered when:
- Same value index displayed, sensor data unchanged
- Only clears value text area (coordinates: 30, 130, 420, 60)
- Layout components (title, label, unit, footer) not redrawn

**Cost:** ~50ms (minimal SPI operation)

#### Layout Component Rendering
- **Full Redraw Case:** Title, separator line, label, unit, footer all drawn
- **Partial Redraw Case:** Only value text updated; layout remains unchanged

**Performance Benefit:**
- Reduces display updates from ~5 redraws/sec to ~0.5 redraws/sec when sensor data is stable
- Eliminates flicker caused by excessive screen clears
- Maintains snappy user experience for button presses (immediate re-layout)

**Implementation Details:**
```cpp
// renderLargeDisplay() logic:
bool doFullRedraw = largeDisplayMode.needsFullRedraw || 
                    value != largeDisplayMode.lastDisplayedValue;

if (doFullRedraw) {
    tft.fillScreen(TFT_BLACK);           // Full clear
    largeDisplayMode.lastDisplayedValue = value;
    // Draw title, label, unit, footer
} else {
    tft.fillRect(30, 130, 420, 60, TFT_BLACK);  // Partial clear
}

// Always update value
tft.drawString(value, 240, 160, 8);
largeDisplayMode.needsFullRedraw = false;  // Clear flag
```

### 10.8 Exit Behavior and Page Redraw

**Trigger:** Button Y pressed while in large display mode (and on same page)

**Action Sequence:**
1. Set `largeDisplayMode.active = false`
2. Set `largeDisplayMode.valueIndex = 0` (reset for next entry)
3. Call `drawCurrentPage(true)` with pageChanged flag
   - This triggers atomic screen clear + complete page layout redraw
   - Works generically for all 10 sensor pages (not page-specific)
   - Prevents visual artifacts from residual large display elements

**Result:** Clean, instant transition back to standard page view with no visual artifacts.

**Why Generic `drawCurrentPage()`?**
Previous implementation (FEATURE-SPEC-004) used page-specific methods:
- `drawHeader()` + `pageIna219()` for INA219 only
- Required custom exit logic per page

Current implementation (FEATURE-SPEC-007) uses unified approach:
- Single `drawCurrentPage(true)` call handles all 10 pages
- Consistent, maintainable, no page-specific exit logic needed
- pageChanged=true flag ensures header/title redraw on transition
